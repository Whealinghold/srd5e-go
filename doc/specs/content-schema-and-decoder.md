## 1. Purpose and scope

Defines the **envelope** in which game content enters the package: the one JSON format version (`schemaVersion`, currently 1), the root object, ids, the decoder that turns a JSON document into a `Set`, or into an error joining **every** problem found (path and kind), the cross-entry checks, the revision table through which content specs request additions, the anti-corruption rules, the use case that runs the decoder with its telemetry, and the `go:embed` rule for bundled data (no generator).

Ownership (shared-types-and-ownership.md FR-035, FR-046, FR-047, FR-053, FR-064, FR-065): this spec owns the envelope, ids, decoder, failure type, the **content identity types** (`ID`, `IDProblem`, `Key`, `Kind`, `Entry`, `MissingContent`; FR-142 to FR-148), **every closed vocabulary type and typed id** (section 3, including `DurationUnit`), `SourceCitation`, the building blocks `NamedText`, `FeatCategory`, `Prerequisite`, `ToolProficiency`, the neutral printed-text family `TextBlock` (FR-150 to FR-152), the **whole-set cross-reference validation** (the only place a reference between entries is resolved; no site is exempt, shared-types-and-ownership.md FR-054) and the embedding rule for bundled data (FR-120, FR-122; FR-121 and FR-123 are withdrawn, there being no generator). Bulk content specs reference these and define none. The shape of each kind's entries is owned by that kind's spec and registered in the revision table (section 5). The baseline registers the root arrays `species`, `backgrounds`, `classes`, `feats`, `spells`, `weapons`, `armor`.

Relations (prose only; the header lists the specs that rank lower, shared-types-and-ownership.md FR-056). The identity types are owned here, so this spec needs nothing from the port spec, which depends on it (shared-types-and-ownership.md FR-064). `Decoder`, `ValidateSet`, the embedded index (FR-122) and the typed ids flow to the `BundledSource` adapter only. Every content data spec depends on this spec and on content-source-port.md, never on another data spec (shared-types-and-ownership.md FR-047). architecture-guardrails.md owns the layout checks of the embedded data (its FR-078).

**Out of scope:**

- The `Source` port, `ContentLookup`, `ContentCatalogue`, `MemorySource`, `BundledSource` (content-source-port.md); licensing, `NOTICE.md` and data layout (content-licensing-and-notice.md).
- The shape, field rules and case tables of each kind of entry (their specs), and the bundled SRD entries themselves (a separate data change).
- Rules behaviour: nothing here computes Armor Class, save DCs or Proficiency Bonus. Class features, traits, benefits and spell effects are faithful SRD text (Q7).
- Encoding back to JSON; `os`, `net/http` or other I/O loading in package `content` (shared-types-and-ownership.md FR-030); detecting a duplicate key inside one JSON object (`encoding/json` keeps the last, Q5).
- A schema version per content spec (shared-types-and-ownership.md FR-034).
- Anything from SRD 5.1 or any other book. Nothing that looked like core fifth-edition material was found missing from the PDF; none is included.

## 3. Vocabulary

All types below are in package `content`, published, owned by this spec. Terms use SRD wording exactly; JSON values for SRD enums use the SRD spelling ("Bludgeoning", "Two-Handed", "Sleight of Hand"); package-invented tags are lower camel case; ids are `[a-z][a-z0-9_]*` (shared-types-and-ownership.md FR-007). Enum values are written by their wire (JSON) spelling; the Go constant is the PascalCase name prefixed by the type (`KindSpell`, `ProblemMissingField`, `DamageBludgeoning`), the zero value of every enum is invalid, and each enum has `String()` (the wire spelling) and `ParseX(string) (X, error)`.

## 4. Requirements

A "problem" is one `Problem` in the error the decoder returns. Paths are JSON Pointers (RFC 6901) from the root (`~` as `~0`, `/` as `~1`; root is `""`). "Reject" means the decoder returns an error holding the stated problem.

| Id | Requirement | Source | Path |
|---|---|---|---|
| FR-001 | The decoder MUST accept a JSON document as `[]byte` and return `(Set, error)`: a `Set` and a nil error for a valid document, otherwise the zero `Set` and an error that is `errors.Join` of one or more `Problem` values (FR-017). A decode failure is untrusted input failing validation, not a port failure: it is an expected result of decoding, read with `Problems(err)` and matched with `errors.Is(err, srderr.ErrInvalidInput)`. The set of outcomes is exactly these two, so a caller switches on `err == nil`. | architecture.md §4, §5, §6; errors-and-results.md FR-023; shared-types-and-ownership.md FR-017 | happy |
| FR-002 | Text that is not valid JSON (including the empty string and whitespace only) MUST produce an error holding exactly one problem: path `""`, kind `syntax`. | architecture.md §5 | unhappy (invalid input) |
| FR-003 | A root value that is valid JSON but not an object MUST be rejected with exactly one problem: path `""`, kind `wrongType`. | architecture.md §5 | unhappy (invalid input) |
| FR-004 | A missing `schemaVersion` MUST be rejected with exactly one problem: path `/schemaVersion`, kind `missingField`. No other field is examined. | architecture.md §5, §7 | unhappy (missing content) |
| FR-005 | A `schemaVersion` that is not an integer value in the sense of FR-021 (a string, `1.5`, `null`, a boolean) MUST be rejected with exactly one problem: path `/schemaVersion`, kind `wrongType`. `1.0` is the integer 1 on every platform and is accepted. A whole number outside the safe-integer range is `unsupportedVersion`. | architecture.md §5 | unhappy (invalid input) |
| FR-006 | An integer `schemaVersion` not in the supported set (0, 2, -1) MUST be rejected with exactly one problem: path `/schemaVersion`, kind `unsupportedVersion`. No other field is examined. | architecture.md §4, §7 | unhappy (missing content: unsupported version) |
| FR-007 | The supported set MUST be exposed as the constant `SchemaVersion = 1` and the function `SupportedSchemaVersions() []int`, which returns a new slice holding exactly the current version (`1`). Revisions requested by content specs add no version (FR-103). | architecture.md §7; shared-types-and-ownership.md FR-034 | happy |
| FR-008 | The root object MUST accept only `schemaVersion` and the optional arrays registered in the revision table. The baseline registers `species`, `backgrounds`, `classes`, `feats`, `spells`, `weapons`, `armor`. An absent array MUST mean no entries of that kind. | architecture.md §5; shared-types-and-ownership.md FR-035 | happy |
| FR-009 | A document containing only `{"schemaVersion": 1}` MUST decode to a `Set` with no entries. | testing.md §4 (empty and minimal) | unhappy (empty case) |
| FR-010 | A root key not accepted by FR-008 MUST be rejected: path `/<key>`, kind `unknownField`. | architecture.md §5, §3 | unhappy (invalid input) |
| FR-011 | A root array field whose value is not an array MUST be rejected at that field (`wrongType`), and an array element that is not an object MUST be rejected at its index (`wrongType`), without examining their children. | architecture.md §5 | unhappy (invalid input) |
| FR-012 | The decoder MUST report every problem found in one pass: problems in several entries, and in several fields of one entry, MUST yield one problem each. | architecture.md §5 | unhappy (invalid input) |
| FR-013 | A value that is missing or of the wrong type MUST NOT produce problems for its children (no cascading): a `features` value that is a string yields one `wrongType`, not one per feature. | architecture.md §5 | unhappy (rule interaction) |
| FR-014 | A `Problem` MUST carry a path and a `ProblemKind` only (a comparable struct with `Path()` and `Kind()`, implementing `error` through a value receiver and unwrapping to `srderr.ErrInvalidInput`); it MUST NOT carry display text beyond the `Error()` rendering, which no code may branch on. | architecture.md §6; errors-and-results.md FR-007 | happy |
| FR-015 | `ProblemKind` MUST be a closed typed enum in package `content` (zero value invalid, `String()` returning the wire spelling) with exactly: `syntax`, `unsupportedVersion`, `missingField`, `unknownField`, `wrongType`, `outOfRange`, `invalidValue`, `duplicate`, `unresolvedReference`, `constraintViolation`. | architecture.md §5, §6 | happy |
| FR-016 | The problem list MUST be deterministic and ordered: root fields in the order `schemaVersion` then the registered arrays in revision-table order; array elements by ascending index; fields of an object in the order the owning kind spec declares; unknown keys after the known fields of the same object, in ordinal order; then, after every entry-level problem, the duplicate-id problems (FR-031) grouped by `Kind` in the declaration order of FR-142 (`species`, `background`, `characterClass`, `feat`, `equipment`, `spell`, `magicItem`, `monster`, `poison`, `trap`, `contagion`; a kind appears only when its row has landed; within `equipment`, `weapons` before `armor`, then further arrays in row order), and inside a group by ascending position of the later entry. So a weapon duplicate precedes a spell duplicate although the root array `spells` precedes `weapons`. Nothing else is cross-entry in a single-document decode (FR-035). The same text MUST always give an equal result (FR-097). | testing.md §4 (determinism) | happy |
| FR-017 | `Problems(err error) []Problem` MUST return every `Problem` held in `err` (flattened through `errors.Join`, in order) as a new slice, and nil for a nil error or an error holding none. The decoder never returns a non-nil error without at least one `Problem` (errors-and-results.md FR-024), and `LoadSetRejected` is built only by `Loader.LoadSet` from a non-empty list: its `Problems()` returns a new slice on every call, so mutating it, or the slice the decoder returned, leaves the result unchanged. | architecture.md §4, §6; errors-and-results.md FR-021, FR-024 | unhappy (immutability) |
| FR-018 | The decoder MUST NOT panic for any `[]byte` input (nil and empty included); every failure to decode, including numbers outside the safe-integer range (FR-021), MUST be a problem, with the same result on every platform and every integer width. | architecture.md §5, §6 | unhappy (invalid input) |
| FR-019 | A required field that is absent MUST be rejected: path of the field, kind `missingField`. | architecture.md §5 | unhappy (missing content) |
| FR-020 | A field whose value is `null` MUST be rejected with kind `wrongType`. Optional fields are expressed by absence, never by `null`. | architecture.md §3 | unhappy (invalid input) |
| FR-021 | A value of the wrong JSON type MUST be rejected with kind `wrongType`. A field declared integer accepts a JSON number whose value is whole, so `2` and `2.0` both mean 2 on every platform (the decoder reads numbers as `json.Number` and decides on the value, not the literal text). `2.5`, a non-finite number, `"2"` and `true` are `wrongType`. A whole number whose magnitude exceeds 2^53 - 1 (9007199254740991), including a 20-digit literal, is `outOfRange` at that field, so the result never depends on platform integer width. The exception is `schemaVersion`, where such a number is `unsupportedVersion` (FR-005). | architecture.md §5 | unhappy (invalid input) |
| FR-022 | A key not declared for an object MUST be rejected at any depth with kind `unknownField`; the decoder MUST NOT ignore it. | architecture.md §5 | unhappy (invalid input) |
| FR-023 | An integer outside the declared inclusive range MUST be rejected with kind `outOfRange`; the range ends are accepted and one beyond each end rejected. | testing.md §4 (boundaries) | unhappy (boundary) |
| FR-024 | An array whose length is outside the declared bounds MUST be rejected at the array's path with kind `outOfRange`. | testing.md §4 (boundaries, empty) | unhappy (boundary) |
| FR-025 | A string that must be one of a closed set (an SRD enum) MUST match exactly, case sensitively, with the SRD spelling; anything else MUST be rejected with kind `invalidValue`. The decoder MUST NOT trim, case-fold, abbreviate or coerce it. | architecture.md §3, §5 | unhappy (invalid input) |
| FR-026 | A repeated member of an array declared a set (for example the same skill twice) MUST be rejected at the index of the later occurrence with kind `duplicate`. | testing.md §4 (duplicate entries) | unhappy (invalid input) |
| FR-027 | A `name` MUST be a non-empty string with no leading or trailing whitespace; otherwise `invalidValue`. | architecture.md §3 | unhappy (invalid input) |
| FR-028 | A `text` MUST contain at least one non-whitespace character; otherwise `invalidValue`. | architecture.md §5 | unhappy (empty case) |
| FR-029 | A `text` and a `name` that pass FR-027 and FR-028 MUST reach the decoded entry unchanged, character for character (typographic apostrophes, line feeds); the decoder MUST NOT trim, wrap, normalise or reword them. | AGENTS.md ("keep it faithful to the source") | happy |
| FR-030 | An `id` MUST match `^[a-z][a-z0-9_]*$` and be at most 64 characters; otherwise `invalidValue`. A conforming id MUST be accepted by `ID` (FR-143) and by the typed id of its kind. | shared-types-and-ownership.md FR-007 | unhappy (boundary) |
| FR-031 | Within one `Kind` ids MUST be unique: a later entry with an id already used in the same kind is rejected at that entry's `id` with kind `duplicate`. The `weapons` and `armor` arrays together form the one kind `equipment`. | testing.md §4 | unhappy (invalid input) |
| FR-032 | The same `id` in two different kinds MUST be accepted (`Key`s differ, FR-145). | architecture.md §3 | unhappy (rule interaction) |
| FR-034 | An entry MAY have a `source` object `{document, section, page}`. When present, all three MUST be present, `document` and `section` non-blank strings, `page` an integer of at least 1; otherwise the usual field problems. When absent the entry is accepted. The decoded value is the `SourceCitation` of FR-115. | AGENTS.md (cite section and page); architecture.md §3 | unhappy (boundary) |
| FR-035 | The decoder of one document MUST NOT resolve a reference to another entry: one document is only part of the set. Every reference site (FR-126) is checked by the whole-set validation (FR-125 to FR-127, FR-140) over the merged documents, never by `JSONDecoder`; the baseline registers `background.feat.featId` (FR-036). No site is exempt and none opts out; a decoder-time scope (the former `sameDocument`) does not exist (shared-types-and-ownership.md FR-054). An entry counts as a target if its `id` is valid (FR-030), even when it has other problems (FR-095). An id that the owning spec resolves inside its own entry (a class row's `featureId`, owned by content-classes.md) is a rule of that kind's shape, not a site. | shared-types-and-ownership.md FR-047, FR-054; SRD 5.2.1, "Parts of a Background: Feat", p. 83 | unhappy (missing content) |
| FR-036 | A background's feat MUST be of category `Origin`. This is the registered site `(background, feat/featId, feat, TargetHasFeatCategory(Origin))` of row R1 (FR-126), so `JSONDecoder` does **not** check it: a background document alone decodes with no problem about its feat. `ValidateSet` reports `unresolvedReference` when no set holds the feat and `constraintViolation` when the feat has another category. The feat shape is owned by content-species-backgrounds-feats.md. | SRD 5.2.1, "Parts of a Background: Feat", p. 83 ("specified Origin feat") | unhappy (rule interaction) |

Every entry MUST implement `Entry` with the key kind of its registered kind (baseline: `species`, `background`, `characterClass`, `feat`, `equipment`, `spell`, so `equipment` precedes `spell`) and the entry's `id`. | FR-146; architecture.md §4 | happy |
| FR-072 | Two `Set`s decoded from equal text MUST be equal under `Set.Equal` (a `Set` holds a slice, so it is not comparable with `==`); documents differing only in entry order MUST decode to equal sets. | architecture.md §3 | happy |
| FR-073 | No decoded type, port or result MAY expose `map[string]any`, `any`, `json.RawMessage`, `json.Number` or other raw JSON; every collection a type returns MUST be a copy. | FR-074 | The decoder MUST NOT accept legacy or other-edition names or aliases: a key such as `races`, `race` or `raceTraits` MUST be `unknownField`; an enum value that is not the SRD 5.2.1 spelling MUST be `invalidValue`. | architecture.md §3, §5 | unhappy (invalid input) |
| FR-075 | The decoder MUST be a pure function of its input: no clock, randomness, I/O or global state, and no `os`, `net` or `io/fs` import. | architecture.md §3, §5, §9 | happy |
| FR-076 | The decoder MUST NOT retain or mutate its input slice, and decoding the same bytes twice MUST give equal results independent of previous calls. | testing.md §4 (determinism, immutability) | unhappy (immutability) |
| FR-077 | `Loader.LoadSet(ctx, cmd)` MUST take a `LoadSetCommand` (the document bytes), call the `Decoder` port once and return its own `LoadSetResult`: `LoadSetLoaded` carrying the port's `Set` for a nil error, and `LoadSetRejected` carrying the port's problems (an equal list, never empty) for an error that holds problems. Generic names such as `Loaded`, `Rejected`, `Decoded` are never exported. | architecture.md §4; shared-types-and-ownership.md FR-017 | happy |
| FR-078 | `Decoder` MUST be a one-method interface declared in package `content` where the use case consumes it (`Decode(document []byte) (Set, error)`): synchronous, in-memory, taking no `ctx`, returning content problems inside its error and never panicking for content. `JSONDecoder` MUST be a zero-value-usable struct in package `content` with `var _ Decoder = JSONDecoder{}`; no facade or re-export package exists. | architecture.md §4, §5, §7 | happy |
| FR-079 | `LoadSet` MUST run inside the span `srd5e.content.load` with a child span `srd5e.content.decode` around the port call, each carrying `srd5e.outcome` (`success` or `failure`; shared-types-and-ownership.md FR-041). | observability.md §5, §6 | happy |
| FR-080 | `LoadSet` MUST increment the counter `srd5e.content.loads` once per call that returns a result or a port-failure error (FR-086), with `srd5e.outcome`. ## 5. Model

### Documents

A document is a JSON object: `{"schemaVersion": 1, "species": [], "backgrounds": [], "classes": [], "feats": [], "spells": [], "weapons": [], "armor": []}` (arrays optional). Field order within an object is the order problems are reported (FR-016); fields marked `?` are optional; JSON names are lower camel case. Every entry starts with `id`, `name`, `source?` (FR-034); the owning kind spec declares the rest.

### Revision table

### Domain types

- **Published by `content`, owned here:** the types of section 3 and section 6. `Problem` and the `Decoder` port live in package `content` beside the use case. Entry value objects are the kind specs' and implement `Entry`. No aggregate, entity or domain event: entries are reference data compared by value. This spec does not use `Die`.
- **Invariants:** each constructor enforces its own spec's rules and returns an error for an invalid instance (`MustX` panics, FR-093). The decoder validates first, collects problems, then constructs; each rule lives once as a constant or predicate (FR-094). Unique ids are enforced per document by the decoder and by `Set`; references and the Origin rule only by `ValidateSet` (FR-035, FR-140). Every problem with untrusted JSON is a `Problem`; no `PortError` is involved in decoding (FR-141).
- **Decoding algorithm (normative for ordering):** (1) parse JSON, else `syntax`; (2) check the root object and `schemaVersion`, stopping on a problem there (FR-004 to FR-006); (3) decode each kind's entries independently, collecting problems; (4) build the lookup set (FR-095); (5) check duplicate ids over it in FR-016 order (FR-031, FR-098); no reference is resolved (FR-035); (6) with no problems, construct the `Set`.

### Versioning and anti-corruption

- After 0.1.0 `schemaVersion` increases whenever a document valid under the previous version would be rejected or read differently (a new kind or required field, a removed or renamed field, a changed enum value set); every increase is **BREAKING** and updates `SupportedSchemaVersions()`. Before 0.1.0 all revisions land as the one version. The decoder supports only the current version; an unsupported one is a single `unsupportedVersion` problem, not a `ContentLookup` variant (shared-types-and-ownership.md FR-034). A set has no version; the SRD edition of an entry is `source.document`. Strictness (FR-022) is what makes a bump necessary.
- Anti-corruption: only `JSONDecoder` knows JSON shapes (FR-073); strict, never lenient (FR-021, FR-022, FR-025); no translation of older editions' terms (FR-074); text verbatim, presentation such as a leading `+` or the "Level 1:" prefix is not stored (FR-029); every problem has a findable path (FR-012, FR-014); bundled content is not trusted more than host content (FR-104); fidelity to the PDF stays a review task (FR-090).

## 7. Observability

Domain types and the `JSONDecoder` adapter are silent by design (observability.md §3, §7): they report through return values and have no retries, fallbacks or I/O timing the use case cannot see. `LoadSet` is instrumented (attribute values: shared-types-and-ownership.md FR-041); the six `srd5e.content.*` signals below are owned here. The seven questions:

1. **What can go wrong?** Not JSON; unsupported version; missing, mistyped, out-of-range or unknown fields; duplicate ids; the decoder port failing (a panic, or an error holding no problem). An unresolved cross-file reference is not a decode problem: `ValidateSet` returns it with no signal (FR-131) and `BundledSource` returns it as a construction error.
2. **How would an operator know?** Error status on the load span, `loads` with `failure`, and `decode_errors` by problem kind.
3. **What is needed to diagnose it?** The paths and kinds in the `LoadSetRejected` the consumer holds; paths never enter attributes (FR-085).
4. **What is counted or timed?** Loads, problems, entries and load duration; the duration has no outcome attribute (the timer starts before the outcome is known; observability.md §5).
5. **Is existing instrumentation still correct?** None exists yet; `decode_errors` carries `srd5e.content.problem_kind`, never `error.type` (FR-100).
6. **What should a consumer monitor?** Any `failure` load or non-zero `decode_errors` for shipped content; a sudden change in `entries_loaded` per kind; a duration regression. A port failure carries `error.type` `content_error` (FR-086), so no failure class is invisible.
7. **Is anything now noisy?** No log (FR-083); no per-entry or per-problem signal.

| Signal | Type | Attributes | Purpose | Suggested monitoring |
|---|---|---|---|---|
| `srd5e.content.load` | span | `srd5e.outcome` (`success`, `failure`) | One load; error status when rejected | Trace any load with error status |
| `srd5e.content.decode` | span (child) | `srd5e.outcome` | The decoding step across the port | Duration against document size |
| `srd5e.content.loads` | counter, `{load}` | `srd5e.outcome`; `error.type` only when the decoder port failed (FR-086) | Loads attempted and how they ended | Alert on any `failure` for shipped data |
| `srd5e.content.decode_errors` | counter, `{problem}` | `srd5e.content.problem_kind` (FR-100) | Problem kinds in rejected documents | Alert when non-zero for shipped data; a rise in `unsupported_version` means a stale consumer document |
| `srd5e.content.entries_loaded` | counter, `{entry}` | `srd5e.content.kind` (FR-101) | Volume loaded by kind | Compare per-kind counts across releases |
| `srd5e.content.load_duration` | histogram, `s` | none (FR-080) | Load time via `telemetry.StartTimer`, also when the port fails | p95 regression against the previous release |

Names and keys are exported constants of package `content` (observability.md §5); all six feed `doc/observability/signals.md` in the same change as the code.
