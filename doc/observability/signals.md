# Signal catalogue

Every metric, span and log event srd5e emits. Must match the code (see
[observability rules](../rules/observability.md), §2 and §10). Consumers use
this to build dashboards and alerts; srd5e cannot run alerts itself.

Add a row for each signal in the same change as its Go constant. A signal
whose code has not landed keeps its planned row in its owning spec
(`doc/specs/`), not here.

## Conventions

- **Name** is the exact string value of the exported constant. It is the wire
  name and stays `srd5e.<context>.<noun>` with snake_case segments, even where
  the Go package name has no underscore (the `d20` package emits
  `srd5e.d20_test.*`, named after the SRD term "D20 Test"). The Go constant
  carries the identifier: `Name` is a column below.
- **Constants** live in a `signals.go` file of the emitting package (for
  example `d20.SpanResolve`), or in `telemetry` for keys shared across
  contexts (`telemetry.AttrOutcome`, `telemetry.AttrErrorType`).
- **Emitted by** names the Go entry point (`package.Type.Method`).
- Attribute values listed here are the closed sets and are binding. They are
  checked in review and by tests that pin them; nothing yet rejects an
  out-of-set value mechanically. O3/O4 (`doc/rules/observability.md` section
  10) will mechanise it.
- Durations are seconds (`s`, float64); counts use UCUM annotations.

## content

Go names: constants in package `content` (`signals.go`); entry point
`content.Loader.LoadSet(ctx, ...)`. `JSONDecoder`, `ValidateSet` and the domain
types are silent: `ValidateSet` (cross-document `duplicate`,
`unresolved_reference` and `constraint_violation` problems) reaches no signal, so
a consumer must read the error it returns. A cancelled `ctx` is returned before
any signal and counted nowhere. Document bytes, paths, ids, names and text never
enter an attribute, and a recovered decoder panic value never reaches a span.

### What to monitor for `character` (the whole of Phase 3)

Phase 3 closed with the O3 audit: every `Span`, `Metric` and `Log` constant of package `character` has a row above with the same value, and
every row names a constant that exists. Three things are worth a dashboard and an alert across all the `character` use cases, whichever one
ran (`srd5e.character.operation`, or `srd5e.class` with `srd5e.feature`):

- **Rejection rate.** The share of `srd5e.outcome` = `failure` with `srd5e.character.result` = `rejected`, split by
  `srd5e.character.rejection`. A rejection is a normal rule outcome and never an error, so alert on a shift, not on a level: a rejection
  that was rare and becomes common (for example `no_uses_remaining` or `not_a_wizard`) usually means the host passes a stale character or
  the wrong class state.
- **Missing-content rate.** Any `srd5e.character.result` = `content_missing`, or a failure that names a missing class, spell, feat or item.
  The bundled slice holds the twelve classes and part of the spells only, so a host that relies on Phase 5 data will see these; alert on any
  nonzero rate in a deployment that supplies the full content set, and on any `error.type` of a content port (`content_error`), which
  is a returned port failure counted once by the use case it left.
- **Duration regressions.** The `.duration` histograms of the use cases (seconds, from the injected clock). All of them are pure CPU over
  small values apart from the content lookups; a p99 that grows past a few milliseconds points at a slow `ContentSource`, not at the rules.

The domain functions emit nothing: a surprising number is read from the result (breakdowns, reasons, events), not from a signal.

## combat

Go names: unexported constants in package `combat` (`signals.go`), written
`combat.metric...`, `combat.attr...`, `combat.value...` below. Every `combat` use case records
the four shared signals through the unexported `combat` instrumenter
(`combat.run`), so none counts its own calls, durations, events or port
failures by hand. The domain (ids, kinds, events, rule options) is silent. Each
later spec adds its own operations (a span `srd5e.combat.<operation>` and a row
for it), its `srd5e.combat.result` values and its extras here. No superseded
name of the earlier combat specs is listed (`combat-foundations.md` section 5).

`srd5e.outcome` is `success` or `failure`; `srd5e.combat.result_class` is
`applied` (success), `refused` (failure, no span error: a normal rule outcome)
or `invalid` (failure, span error status). `outcome=failure` therefore covers
every refusal and is not by itself an alarm.

### What to monitor for `combat` (the whole of Phase 4)

Phase 4 closed with a catalogue audit: every combat name (prefix srd5e.combat) in `combat/signals.go` has a row above and every row names a name
that exists (`TestSignalCatalogueEqualsTheConstants` pins both directions), and none of the superseded names of
`combat-foundations.md` section 5 is listed. The per-spec paragraphs above give the detail of each family; across all `combat` use cases,
whichever ran (`srd5e.combat.operation`), these are the things worth a dashboard and an alert. The thresholds are starting points from
`combat-foundations.md`; tune them to the host's volume.

- **Errors.** Any increment of `srd5e.combat.errors`, split by `error.type` (`dice_roller_error`, `content_error`). It counts a returned
  port failure once, at the use case it left, so a nonzero rate is an infrastructure fault in the host's roller or content source, never a
  rule outcome. A cancelled `ctx` is returned as `ctx.Err()` and counted nowhere.
- **Invalid results.** The `invalid` share (`srd5e.combat.result_class`) of one operation above 1 percent of its calls over 15 minutes.
  `invalid` is a host fault (an unknown `CombatantID`, a forged or zero value, a `content_missing` stat block, a malformed command) and carries
  error status on the span, so it separates from a refusal.
- **Refused share.** The `refused` share per operation and per `srd5e.combat.result`. A refusal is a normal rule outcome with no error status,
  so `srd5e.outcome` = `failure` alone is not an alarm (it includes every refusal). Alert on a shift, not on a level: a reason that was rare
  and becomes common (`not_active_combatant`, `action_already_taken`, `insufficient_movement`, `combatant_is_dead`, `ledger_refused`) means the
  host is out of step with the tracker, the ledger or the roster it holds.
- **Limits.** Any `limit_exceeded` result. It means a call met a cap of plan P10 (256 combatants per encounter, 64 active effects per creature,
  64 ongoing spells per target, 32 summons per summoner, 4096 events per call, 1000 cascade steps per call) and was refused with its input
  unchanged. A host that keeps hitting one is leaking combatants, effects or summons rather than ending them.
- **Latency.** The p99 of `srd5e.combat.operation_duration` above 10 ms for 5 minutes. The domain is pure CPU over small values, so a slow
  call is a slow `dice.Roller` or `ContentSource`, or a roster near its cap, not the rules.
- **Rates that shift.** The `critical_hit` share of `resolve_attack` per roll mode against 5, 9.75 and 0.25 percent; the mix of
  `srd5e.combat.concentration_outcome` (a rising `broken` share is damage that is not being absorbed); `srd5e.combat.deaths` by
  `srd5e.combat.death_cause`; the p99 of `srd5e.combat.encounter_size` and of the `*_in_force` and `*.active` histograms, which only grow when
  the host does not end holds, grapples, effects or zones.

The domain files emit nothing: a surprising number is read from the result (breakdowns, reasons, events) and from `srd5e.combat.events`,
which counts turns, rounds and every event by kind.
